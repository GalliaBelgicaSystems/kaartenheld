1. [MEDIUM] Re-talking to the Heal Mage (or opening a chest) during the chest
   jingle tail silently drops the jingle and mis-times the `MUSIC_TOWN` restore
   ----------------------------------------------------------------------------
   Files:
     - src/audio/audio.c:107-130 (`audio_play_music`)
     - src/audio/huge_music_banked.c:66-92 (`music_play_banked`)
     - src/game/jingle_full_banked.c:127-146 (`jingle_full_banked`)
     - src/core/event.c:145-167 (`EVENT_ACTION_PLAY_MUSIC`)

   Details:
   Talking to the Heal Mage runs `EVENT_ACTION_PLAY_MUSIC` with `MUSIC_CHEST`,
   which calls `audio_play_music(MUSIC_CHEST)`. Unlike chests (which set a
   `CHEST_*_TAKEN` flag and cannot be triggered twice in a row), the Heal Mage
   has `flag_required = FLAG_NONE` and is repeatable at any time.

   `MUSIC_CHEST` plays a 3-note arpeggio (~15 tracker ticks) followed by a
   silent pause until `jingle_full_banked` restores `MUSIC_TOWN` at either:
     - `g_vbl_music_ticks >= 80` (~1.25s = ~75 frames on hardware / mGBA), or
     - `g_jingle_frames >= 240` (4.0s under the SameBoy harness where VBL does
       not fire inside `WAIT`).

   If the player mashes `A` through the Heal Mage's dialogue (3 page advances,
   can complete in < 15 frames) and immediately interacts with the Heal Mage a
   second time while `g_audio_current_track` is STILL `MUSIC_CHEST`:
     a) `audio_play_music(MUSIC_CHEST)` hits:
          if (g_audio_current_track == track) return;   // src/audio/audio.c:110
        and becomes a complete no-op: the arpeggio does NOT replay,
        `g_vbl_music_ticks` is NOT reset, and `EVENT_MUSIC_CHANGED` is NOT
        emitted.
     b) Even if `audio_play_music` allowed re-triggering one-shot tracks,
        `music_play_banked` (`src/audio/huge_music_banked.c:66`) resets
        `g_title_frames = 0` for `MUSIC_TITLE`, but never resets
        `g_jingle_frames = 0` for `MUSIC_CHEST`. Under the harness backstop,
        a second `MUSIC_CHEST` triggered after `MUSIC_TOWN` or during
        `MUSIC_CHEST` would inherit a non-zero `g_jingle_frames` unless the
        previous jingle completed its full 240-frame cycle.

   Recommendation:
   - In `audio_play_music(uint8_t track)` (`src/audio/audio.c:110`), allow
     re-triggering one-shot tracks (`track != MUSIC_CHEST && track != MUSIC_TITLE`
     on the early-return guard), or reset/restart when `track == MUSIC_CHEST`.
   - In `music_play_banked(uint8_t track)` (`src/audio/huge_music_banked.c:83`),
     declare `extern volatile uint8_t g_jingle_frames;` and reset
     `g_jingle_frames = 0u;` inside the `case MUSIC_CHEST:` branch (mirroring
     `g_title_frames = 0u;` in `case MUSIC_TITLE:`).


2. [MEDIUM] Duplicate `"npc_wizard"` 2bpp tile in `enemy_ow_tiles.h` wastes 1 of
   the last 2 OAM tiles in the hard 100..127 budget + unpinned NPC tail order
   ----------------------------------------------------------------------------
   Files:
     - tools/screen_compiler/battle_compile.py:147 (`OW_ORDER_PINNED`)
     - tools/screen_compiler/battle_compile.py:563-597 (`ow_blob_layout`)
     - screens/enemy_types/npc_heal_mage.json
     - screens/enemy_types/npc_wizard.json
     - src/gfx/enemy_ow_tiles.h
     - src/game/enemy_ow_count.c (`g_enemy_ow_tile_count = 27`)

   Details:
   a) Tile duplication:
      `npc_heal_mage.json` (`"cells": ["npc_wizard"], "palette": "sprites8"`)
      and `npc_wizard.json` (`"cells": ["npc_wizard"], "palette": "sprites7"`)
      use the exact same 16-byte 2bpp tile (`"npc_wizard"` at sheet `(5, 3)`),
      differing only in their CGB OBJ palette slot (7 vs 5).
      Because `ow_blob_layout()` appends `et['overworld']['cells']` per enemy
      type without deduplicating identical cell sequences, `"npc_wizard"` is
      emitted twice in `src/gfx/enemy_ow_tiles.h`:
        - blob index 17 (VRAM tile 117 / `0x8750`) for `npc_heal_mage`
        - blob index 20 (VRAM tile 120 / `0x8780`) for `npc_wizard`
      With `g_enemy_ow_tile_count = 27` out of the hard 28-tile ceiling (tiles
      100..127 before colliding with BG Block 1 at tile 128 / `0x8800`), only
      **1 tile** of headroom remains. Deduplicating identical `cells` tuples in
      `ow_blob_layout()` (mapping `npc_heal_mage` and `npc_wizard` to the same
      tile offset while preserving each entry's distinct palette in
      `g_enemy_ow_palettes[]`) immediately reclaims 1 OAM tile (26/28) and also
      keeps every existing NPC/rider tile index unchanged!

   b) `OW_ORDER_PINNED` vs. comments in `verify_oam.py` / `verify_vram.py`:
      `verify_oam.py:236` and `verify_vram.py:216` state that `ow_blob_layout`
      is "append-only; pinned prefix never moves", yet `OW_ORDER_PINNED` in
      `battle_compile.py:147` only pins the original 6 enemies:
        `['bat', 'kobold', 'mimic', 'slime', 'slime_lord', 'spider']`
      All NPCs (`npc_dog`, `npc_guard`, `npc_heal_mage`, `npc_mayor`,
      `npc_merchant`, `npc_wizard`, `slime_knight`, `treasure_chest`) are in the
      alphabetically sorted tail, so inserting `npc_heal_mage` shifted
      `npc_mayor`, `npc_merchant`, `npc_wizard`, `slime_knight`,
      `treasure_chest`, and all 3 `RIDER_TILE_*` defines by +1 across 13 files.
      Either deduplicate shared `cells` in `ow_blob_layout()` or extend
      `OW_ORDER_PINNED` to include existing NPCs so future additions are truly
      append-only.

   dialogue pages
   ----------------------------------------------------------------------------
   Files:
     - screens/dialogue/heal_mage.json
     - src/core/dialogue.c:66-74 (`dialogue_next`)

   Details:
   The dialogue engine renders 3 lines per page and advances by 3 lines on each
   `A` press (`uint8_t next = d->current_line + 3;`).
   `screens/dialogue/heal_mage.json` has 7 lines, which splits two sentences
   across page boundaries:
     - Page 1 (lines 0..2):
         "Let me heal your"
         "wounds!"
         "With a ring card,"      <-- dangling clause at bottom of page 1
     - Page 2 (lines 3..5):
         "you can get healed"
         "during combat."
         "The merchant"           <-- dangling subject at bottom of page 2
     - Page 3 (line 6):
         "sells one!"             <-- orphaned single line on page 3

   Compare `screens/dialogue/dog_greeting.json` and `quest_complete.json`, which
   pad with `""` so every 3-line page is self-contained.
   Inserting `""` after `"wounds!"` (8 lines total = `MAX_DIALOGUE_LINES`, still
   3 pages / 3 `A` presses, so `tools/scenarios/tests/heal_mage.json` needs no
   input changes) yields clean pages:
     - Page 1: "Let me heal your" / "wounds!" / ""
     - Page 2: "With a ring card," / "you can get healed" / "during combat."
     - Page 3: "The merchant" / "sells one!"


5. [MEDIUM] No size/content guard between `src/gfx/enemy_ow_tiles.h` and
   `g_enemy_ow_tile_count`; `png2gb.py --tile-coords ""` still falls back to
   full-sheet encoding
   ----------------------------------------------------------------------------
   Files:
     - tools/png2gb.py:254-260 (`encode_png`)
     - tools/screen_compiler/battle_compile.py:729-755, 1351-1358, 1509-1529
     - src/game/enemy_ow_content.c:13-22
     - tools/verify_vram.py:217-237

   Details:
   Commit `dc33d03c` fixed the root cause of the `9f69667d` OAM overflow (where
   `battle_compile.py --ow-coords` crashed on `hero_json=None` and piped `""` to
   `png2gb.py --tile-coords ""`, dumping all 32 sheet tiles into
   `src/gfx/enemy_ow_tiles.h`). However, three defense-in-depth gaps remain:

   a) `tools/png2gb.py:254` checks `if tile_coords:` (truthiness) instead of
      `if tile_coords is not None:`. Passing `--tile-coords ""` from any caller
      sets `tile_coords = ""` (falsy) and silently falls through to the `else:`
      branch (row-major full-sheet dump). Changing line 254 to
      `if tile_coords is not None:` and raising `Png2GbError` when `coords_list`
      is empty eliminates the silent fallback in `png2gb.py` itself.
   b) `battle_compile.py --gfx-coords` (`lines 1351-1358`) does not have the
      `if not coords: return 1` check that `dc33d03c` added to `--ow-coords`
      (`lines 1460-1462`).
   c) In `9f69667d`, `g_enemy_ow_tile_count` was `27` (432 B) while
      `enemy_ow_tiles[]` was `512` bytes (32 tiles), yet `battle_compile.py
      --check` and `verify_vram.py` both passed!
      - `battle_compile.py --check` (`lines 1509-1529`) checks
        `enemy_ow_count.c` but never verifies that `src/gfx/enemy_ow_tiles.h`
        has `ow_count * 16` bytes (`enemy_ow_tiles[432]`).
      - `verify_vram.py` (`lines 217-237`) compares VRAM against bytes parsed
        from `src/gfx/enemy_ow_tiles.h` itself, which is tautological if
        `enemy_ow_tiles.h` was generated with the wrong tile order because
        `ui_sprite_init` copies `enemy_ow_tiles` into VRAM.
      - Adding `_Static_assert` / a compile-time array-size check or validating
        `enemy_ow_tiles.h` length in `battle_compile.py --check` will catch any
        stale `enemy_ow_tiles.h` immediately.
